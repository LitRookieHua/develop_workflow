# lark-messaging：飞书操作规则（通知与问答）

对外飞书沟通分两类：**通知**（单向）与**问答**（双向）。先分类再发消息，两类格式与后续动作不同。

分工（各查各的权威源）：

| 内容 | 权威源 |
| --- | --- |
| 发送/回复监控命令、open_id 语义 | lark-im skill（`lark-cli im +messages-send --as user --user-id <ou_xxx> --text "..."`） |
| PR 通知对象（按仓库的 owner 名单与 open_id） | [pr-merge.md](pr-merge.md) §2 |
| 需求/问题创建人的查找 | lark-contact skill（`lark-cli contact +search-user --query "名字" --as user`） |
| **何时通知、何时问答、消息格式** | 本文档 |

## 1. 通知（单向，发完即止）

**适用场景**：

- PR 提交后（请人审核、请人强行合入）
- 需求开发完成
- 问题解决完成

**动作**：发送即完成，**不需要对方回复，不做回复监控**。

**格式（三行）**：

```
<开发功能/解决问题>
<PR链接>/<jira单链接>
<具体事项，例如：帮忙PR/帮忙强行合入/功能已完成/问题已修复>
```

示例：

```
N60 DTC表V4.0更新
https://bitbucket.imotion.ai:7990/projects/MCU/repos/mcu_app_j6/pull-requests/1645
帮忙PR
```

## 2. 问答（双向，必须拿到答案）

**适用场景**：

- 需求开发过程中对需求有需要补充/确认的——询问**需求创建人**
- 问题分析过程中对问题有需要补充/确认的——询问**问题创建人**

**动作**：发送后二选一拿到答案，**未得到答案前不擅自假设、不推进依赖该答案的步骤**：

1. **等待对方飞书回复**（监控回复，如定时轮询会话消息或用户转告）
2. **用户在终端直接给答案**（用户自己知道答案时，跳过等待）

**格式（三行）**：

```
<开发功能/解决问题>
<PR链接>/<jira单链接>
<具体问题，例如：该功能需要合入哪些分支/等等>
```

示例：

```
N60 0x28服务通信类型参数01常规应用报文支持
https://jira.imotion.ai:7070/browse/IDC310BAIC-1417
该功能需要合入哪些分支？
```

## 3. 通用约定

- **不用"您好"等客套开场，直接说事**（2026-10-22 用户规则）
- 身份一律 `--as user`（bot 身份会显示为机器人）
- open_id 查询用 lark-contact skill；搜索命中多人且后续操作有副作用时列候选给用户挑，不擅自选第一条
- 多行消息的换行：bash 双引号里 `\n` 不会被转义（会原样发出字面 `\n`），必须用 ANSI-C 引号 `$'...\n...'` 让 bash 转成真实换行再传给 lark-cli，lark-cli 本身不做二次反转义（2026-10-26 踩坑后补此规则）
