## 一、 概述 (Overview)

### 1.1 功能背景与目标

* **业务背景与痛点**：T68 产线 PKI 丢失问题暴露出 A 核 uds_service 被动接收 R 核推送 url/port 的模式不可靠——R 核未推送或 A 核未收到时，A 核本地无 url/port 可用且无法补取。方案0 决定：A 核改为"查不到就主动向 R 核要"（J6BREQ-14319），同时产线标定流程需要 `22 9A 95` 查询 PKI 证书可用性，而证书实际持有方在 A 核，R 核必须转发查询（J6BREQ-14320）。
* **核心目标**：
  1. R 核 mcu-dcm 支持 A 核发起的 `22 9A 3E` 查询，从 NVM Z021 读 url/port 并应答 `62 9A 3E` + 车型实际长度负载
  2. 诊断仪 `22 9A 95` 时 R 核经 IPC 转发给 A 核判定证书可用性，组装 `62 9A 95` + 2 字节应答；超时回 NRC 0x22
* **设计原则**：复用 IpcDiagSvc 既有通道（Ins3ch3 / GroupID 0x0303）与既有代码模式（HandleAutoResponse 自动应答、0x2104 读 handler 状态机），不新增通道与协议头。

### 1.2 适用范围 (Scope)

* **适用平台**：mcu_app_j6（cpj_gac），变体 s52 / s52-e046 / t09 / t51 / t68 / t75 / t88，分支 develop（release 分支本次不做，按用户指令）
* **核心职责**：R 核侧两个新 IPC 交互：sidfunction 0x2238 自动应答（9A3E）；sidfunction 0x2E12 转发查询（9A95）
* **范围边界**：A 核侧主动查询触发/重试/落盘 fsync（J6BREQ-14318/14319 A 核部分）与 A 核证书可用性判定逻辑不在本设计内；V20/996D（luna6/t996d 变体）不在本次改动范围

### 1.3 术语与缩略语

| 缩略语/术语 | 全称 | 本文中含义 |
| :--- | :--- | :--- |
| AR IPC | A-R core IPC | A 核（Linux 侧 uds_service）与 R 核（mcu-dcm）间诊断转发通道，Ins3ch3 / GroupID 0x0303 |
| sidfunction | IPC AppHeader 32-bit key | A-R 帧的业务键，应答匹配依据（0x2E06 写 9A3E / 0x2238 读 9A3E / 0x2E12 读 9A95） |

### 1.5 设计约束与假设

* **技术约束**：IPC 帧 3 字节 UDS 协议头（SID+DID 两字节）+ 数据，与既有 2E06 写路径一致；应答长度按变体 Z021 NVM block 长度宏自动适配（不写死 30/46）
* **外部假设**：A 核 uds_service 侧同步实现 0x2238 请求方与 0x2E12 应答方（联调对端）
* **假设的验证方式**：台架联调阶段与 A 核团队核对通道契约；9A3E 路径可用 NVM 写入值回读验证，9A95 路径依赖 A 核应答

## 二、 架构设计与模块间交互 (Architecture & Interaction)

### 2.1 模块依赖关系与调用链

* **14319（9A3E 应答）**：A 核 uds_service ➡️ IPC(0x0303/0x2238) ➡️ R 核 `IpcAdpr_Svc_RxCallback_DID` ➡️ `IpcDiagSvc_HandleAutoResponse`（新增 0x2238 分支）➡️ 读 NVM Z021 ➡️ `IpcDiagSvc_SendTracked` 回 `62 9A 3E`+负载
* **14320（9A95 转发）**：诊断仪 `22 9A 95` ➡️ DCM 0x22 框架 ➡️ 变体 ReadHandler_0x9A95（改为 IPC 状态机）➡️ IPC(0x0303/0x2E12) ➡️ A 核 uds_service 判定 ➡️ 应答状态字节 ➡️ R 核组装 `62 9A 95`+2B 回诊断仪

### 2.2 接口规范定义

| 接口类型 | 函数原型 / 帧格式 | 输入/输出 | 核心职责 |
| :--- | :--- | :--- | :--- |
| IPC 帧（A→R） | `22 9A 3E`，sidfunction=0x2238 | — | A 核 url/port 查询请求 |
| IPC 帧（R→A） | `62 9A 3E` + Z021 负载，sidfunction=0x2238 | 负载 30B（常规）/46B（t75） | R 核应答 |
| IPC 帧（R→A） | `22 9A 95`，sidfunction=0x2E12 | — | R 核转发证书状态查询 |

| 静态函数（新增） | `IpcDiagSvc_ResponsePkiUrlPort()` | 无参，写 `g_IpcDiagSvc_ResponseData_au8` | 14319 应答数据组装 |

### 2.3 并发与调度上下文

| 接口 / 共享资源 | 执行上下文 | 临界区保护方式 | 备注 |

## 三、 核心逻辑、状态机与参数规则

### 3.1 14319：HandleAutoResponse 新增 0x2238 自动应答分支

7 个变体 `cpj_gac/ipc_cfg/<v>/src/IpcDiagSvc.cpp` 的 `IpcDiagSvc_HandleAutoResponse` 中，仿照 0x0702（GetVersionInfo）分支新增：

```text
else if ((channel == IPCADPR_DID_CHANNEL) && (sidfunction == 0x2238u))
{
    IpcDiagSvc_ResponsePkiUrlPort();
    (void)IpcDiagSvc_SendTracked((uint16)channel, g_IpcDiagSvc_ResponseData_au8,
                                  g_IpcDiagSvc_ResponseDataLen, 0u, sidfunction);
    LogSync("[IpcDiagSvc] AutoResp PkiUrlPort sent on ch=%u sidf=0x%08X\r\n", ...);
}
```

`IpcDiagSvc_ResponsePkiUrlPort()`（新增静态函数，仿 `ResponseGetVersionInfo`）：

```text
1. memset 清空 g_IpcDiagSvc_ResponseData_au8 / Len
2. g_IpcDiagSvc_ResponseData_au8[0..2] = 0x62, 0x9A, 0x3E   /* 正响应头，t75 亦回 9A3E（AR IPC 契约不变，同 7483） */
3. idia::idiaIdBasedReadWrite(Z021, E_DIA_READ_REQUEST, &buf[3], NVM_CFG_NV_BLOCK_LENGTH_NVM_PDM_Z021_PkiInformation)
4. g_IpcDiagSvc_ResponseDataLen = 3 + Z021长度宏
```

长度由各变体 `pdm_cfg.h` 的 `NVM_CFG_NV_BLOCK_LENGTH_NVM_PDM_Z021_PkiInformation` 宏决定（s52 等常规 30，t75 46），自动适配、不写死。

### 3.2 14320：9A95 ReadHandler 改 IPC 往返状态机

仿 `gType_ov_dia_DID_ReadHandler_0x2104`（三步状态机）重写各变体 `gType_ov_dia_DID_ReadHandler_0x9A95`：

| 当前状态 | 目标状态 | 触发条件 | 动作 |
| :--- | :--- | :--- | :--- |
| IDLE/未发送 | GET_STATE | 首次进入 | `IpcDiagSvc_SendTracked(IPCADPR_DID_CHANNEL, {0x22,0x9A,0x95}, 3, DIA_IPC_SSH_TIMEOUT_MS=2000, 0x2E12)`，返回 `E_DID_BUSY` |
| GET_STATE | GET_DATA | `GetReqState(0x2E12)==POS` | 返回 `E_DID_BUSY`（DCM 框架继续 pending 0x78 轮询） |
| GET_STATE | IDLE（重发） | state 为 NEG/TIMEOUT 且重试次数超限 | 返回 `E_DID_ERROR` → 框架转 NRC 0x22（conditionsNotCorrect） |
| GET_DATA | DONE | `GetRespData(0x2E12, 0x9A95)` E_OK 且 `respPtr[0..2]==62 9A 95` | 写 `f_readDataBuffer_u8_p[0..1]`（DID 表长度 2），返回 `E_DID_OK` |

* 超时重试上限与 14319 需求对齐（A 核侧重试 3 次；R 核侧转发等待取 2s IPC 超时 + 有限重发，超限回 NRC 0x22，不无限等待）
* t51/t88 无 9A95 表项：lookup 表新增 `{0x9A95, 2, ...}` 条目（保持表升序）+ hpp 声明 `DID_LENGTH_0x9A95 2u` + ReadHandler 实现
* 其余 5 变体：替换空壳 ReadHandler 实现，表项不动

### 3.3 可配置参数

| 参数 | 取值 | 说明 |
| :--- | :--- | :--- |
| `IPCADPR_DID_CHANNEL` | 既有 0x0303 通道 | 不新增通道 |
| IPC 超时（9A95） | `IPCDIAGSVC_RESPONSE_TIMEOUT_MS`（5s）或 2s | 开发时定，倾向与 0x2104 一致 |
| 重试次数 | 3 | 与 A 核侧 9A6E 方案对齐 |

## 五、 异常处理、容错与安全机制

| 异常场景 | 防御策略 |
| :--- | :--- |
| Z021 NVM 读失败 / 内容全 0xFF | 照常应答（内容无效由 A 核校验并走重试，与 14319 A 核侧重试语义衔接） |
| 9A95 IPC 超时 / 应答校验失败 | 有限重发后 `E_DID_ERROR` → NRC 0x22，不无限等待（需求明确） |
| 应答帧长度异常 | `GetRespData` 后校验 `respPtr[0..2]` 与 respLen，不匹配按失败重试 |
| 状态机残留（上一请求未完成新请求进入） | static 状态机随 DCM 请求生命周期，超时路径收敛回 IDLE（同 0x2104 模式） |
